# 原子提交规范

## 目标
- 确保每次改动都是单主题、可回退、可验证、可解释的。
- 避免在超大型项目中出现“一个提交混入多个方向改动”导致的回归和追责困难。

## 原子化规则
- 每次提交只做一类变化：
  - 只建文档
  - 只建目录和索引
  - 只补一类基线文档
  - 只补一类构建治理
  - 只补一类安全治理
  - 只补一类测试设施
  - 只补一类 CI 或门禁配置
- 一个提交不允许同时混入：
  - 文档结构
  - 构建逻辑
  - 测试设施
  - 业务功能
- 每次提交完成后必须：
  - 更新相关文档状态
  - 更新验证看板中的对应项
  - 如有偏差，登记 `decision-log.md`
  - 立即执行 Git commit

## 推荐提交粒度
- 文档骨架单独提交
- 阶段文档单独提交
- 验证看板和决策日志单独提交
- Phase 0 基线盘点按主题拆分：
  - 核心路径矩阵
  - 资产清单
  - 测量协议与设备矩阵
  - 风险与禁区清单
  - 测试数据方案
  - kill switch 方案
- 构建治理按主题拆分：
  - 版本与插件收口
  - release 构建生产化
  - endpoint 收口
  - 权限治理
  - migration 治理
  - WebView 安全策略
- 测试治理按主题拆分：
  - `src/test` 基础设施
  - 首批 JVM tests
  - fixture/fake data
  - Bridge contract tests
  - smoke
  - CI workflow

## 中文 commit message 规范
- `docs: 新增重构总入口与总路线图`
- `docs: 新增 Phase 0至2 阶段执行计划`
- `docs: 新增验证看板与原子提交规范`
- `docs: 补充 Phase 0 核心路径与资产清单`
- `docs: 补充 Phase 0 测量协议与风险清单`
- `build: 收口 Android 构建版本与变体配置`
- `security: 收紧 Android 网络与权限策略`
- `test: 建立 Android JVM 单测基础设施`
- `ci: 新增 Android 质量门禁工作流`

## 评审检查项
- 改动是否只围绕一个主题。
- 改动是否具备回滚路径。
- 改动是否有对应验证项。
- 改动是否已经同步更新文档和看板。
- 提交信息是否准确、中文且能反映主题。
